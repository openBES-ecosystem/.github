# Contributing to openBES-ecosystem

Thank you for your interest in contributing to the openBES-ecosystem! This document provides guidelines for contributing to our open research ecosystem for building energy simulation.

## 🌟 How to Contribute

We welcome contributions in many forms:

- **Code**: New features, bug fixes, and performance improvements
- **Documentation**: README updates, tutorials, examples, and API documentation
- **Research**: Validation studies, case studies, and benchmark datasets
- **Testing**: Unit tests, integration tests, and validation test cases
- **Issues**: Bug reports, feature requests, and documentation improvements
- **Discussions**: Ideas, questions, and best practices

## 🚀 Getting Started

1. **Fork and Clone**: Fork the repository you want to contribute to and clone it locally
2. **Create a Branch**: Create a feature branch from `main` (e.g., `feature/add-simulation-module`)
3. **Make Changes**: Implement your changes following our coding standards
4. **Test**: Ensure all tests pass and add new tests for your changes
5. **Commit**: Write clear, descriptive commit messages
6. **Push**: Push your changes to your fork
7. **Pull Request**: Open a pull request with a detailed description

## 📝 Pull Request Guidelines

When submitting a pull request:

- **Title**: Use a clear, descriptive title
- **Description**: Explain what changes you made and why
- **Testing**: Describe how you tested your changes
- **Documentation**: Update relevant documentation
- **Breaking Changes**: Clearly note any breaking changes
- **Related Issues**: Reference any related issues (e.g., "Fixes #123")

### Pull Request Checklist

- [ ] Code follows the repository's style guidelines
- [ ] Tests added/updated and passing
- [ ] Documentation updated (if applicable)
- [ ] No breaking changes (or clearly documented)
- [ ] Commits are clear and well-organized
- [ ] Self-review completed

## 🐛 Reporting Bugs

When reporting bugs, please include:

- **Description**: Clear description of the bug
- **Reproduction Steps**: Step-by-step instructions to reproduce
- **Expected Behavior**: What you expected to happen
- **Actual Behavior**: What actually happened
- **Environment**: OS, software versions, relevant configuration
- **Screenshots**: If applicable, add screenshots
- **Error Messages**: Include full error messages and stack traces

## 💡 Suggesting Features

When suggesting features:

- **Use Case**: Describe the problem or use case
- **Proposed Solution**: Explain your proposed approach
- **Alternatives**: Describe alternative solutions you've considered
- **Context**: Provide context about building energy simulation needs
- **Impact**: Explain how this benefits the research community

## 🔬 Research Contributions

For research-focused contributions:

- **Validation**: Provide validation against established benchmarks or empirical data
- **Reproducibility**: Include data, scripts, and instructions to reproduce results
- **Documentation**: Document assumptions, limitations, and methodology
- **References**: Cite relevant literature and standards
- **Open Data**: Use or create open datasets when possible

## 💻 Coding Standards

### General Guidelines

- Write clear, readable, and maintainable code
- Follow the existing code style in each repository
- Use meaningful variable and function names
- Add comments for complex logic
- Keep functions focused and modular

### Documentation

- Document public APIs and functions
- Include docstrings with parameter descriptions
- Provide usage examples where helpful
- Keep README files up to date

### Testing

- Write unit tests for new functionality
- Ensure tests are reproducible
- Test edge cases and error conditions
- Maintain or improve code coverage

## 🔒 Security

If you discover a security vulnerability:

- **Do not** open a public issue
- Review our [Security Policy](SECURITY.md)
- Report vulnerabilities through appropriate channels
- Allow time for the issue to be addressed before disclosure

## 📚 Documentation Standards

- Use clear, concise language
- Provide practical examples
- Include context about building energy simulation
- Keep technical accuracy high
- Update documentation with code changes

## 🌍 Open Research Principles

Contributions should align with our open research values:

- **Transparency**: Methods and data should be open and documented
- **Reproducibility**: Results should be reproducible by others
- **Collaboration**: Work cooperatively with the community
- **Quality**: Maintain high scientific and technical standards
- **Accessibility**: Make tools and documentation accessible to diverse users

## 📬 Communication

- **Issues**: Use GitHub Issues for bugs and feature requests
- **Discussions**: Use GitHub Discussions for questions and ideas
- **Pull Requests**: Use PR comments for code review discussions
- **Respect**: Follow our [Code of Conduct](CODE_OF_CONDUCT.md)

## ⚖️ Licensing

By contributing, you agree that your contributions will be licensed under the same license as the project you're contributing to. Most repositories in this ecosystem use open-source licenses compatible with open research.

## 🙏 Recognition

We value all contributions! Contributors will be:

- Acknowledged in release notes
- Listed in project documentation
- Recognized in publications where appropriate
- Credited in citation files (CITATION.cff)

## ❓ Questions?

If you have questions:

1. Check the repository's README and documentation
2. Search existing issues and discussions
3. Open a new discussion for general questions
4. Open an issue for specific bugs or feature requests

Thank you for contributing to sustainable building design through open research! 🌿
